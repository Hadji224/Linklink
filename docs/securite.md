# Sécurité — contrôles par risque (OWASP Top 10)

| Risque | Mesures dans LinkLink |
| --- | --- |
| **A01 Contrôle d'accès** | Toutes les règles côté serveur (`server/src/perm.ts`) : projets invisibles (404) pour les non-membres invités, messages directs réservés à leurs deux participants, fichiers filtrés par niveau de confidentialité, annonces réservées au PDG, au Chargé de communication et à l'administrateur technique ; capacités calculées côté serveur par fonction et par mandat (`can`), refus journalisés, matrice de permissions testée automatiquement. Le temps réel n'envoie les données privées qu'aux personnes autorisées. |
| **A02 Cryptographie** | Mots de passe hachés avec **scrypt** (sel aléatoire, comparaison à temps constant ; les anciens hachages bcrypt restent valables et sont remplacés au prochain login) ; sessions JWT signées de **7 jours, renouvelées tant que la personne utilise l'application** (en-tête `X-Refreshed-Token`) ; « Déconnecter tous mes appareils » ; HTTPS + HSTS en production ; secret via `JWT_SECRET`. |
| **A03 Injection** | Requêtes SQL paramétrées exclusivement ; validation de toutes les entrées (zod) ; React échappe le contenu (aucun HTML injecté), liens en `rel="noopener noreferrer"`. |
| **A04 Conception** | Inscription sur invitation seulement (**code qui expire après 30 jours**, jamais écrit dans les journaux), **premier compte protégé par `BOOTSTRAP_SECRET`** sur un serveur hébergé (sans ce secret : inscription verrouillée), consentement explicite, séparation des pouvoirs (PDG ≠ Caissier, double approbation), accès d'urgence borné (deux détenteurs, 2 h), suppression en cascade. |
| **A05 Configuration** | En-têtes : CSP stricte, `X-Frame-Options: DENY`, `nosniff`, `Referrer-Policy`, `Permissions-Policy`, COOP, HSTS. |
| **A06 Composants** | Dépendances minimales, `npm audit` sans vulnérabilité connue lors de la livraison. |
| **A07 Authentification** | **Anti force brute en base** (valable sur plusieurs instances) : seuls les échecs comptent, limités par adresse IP *et* par compte (blocage temporaire, notification au PDG et à l'administrateur) ; s'applique aussi à l'inscription (mauvais code d'invitation), au changement de mot de passe, à la suppression de compte et au code d'urgence ; **WebSocket par ticket à usage unique (30 s)** — le jeton de session ne circule plus dans une adresse — avec contrôle de l'origine ; changement de mot de passe ou de rôle = anciennes sessions invalidées ; jeton en en-tête `Authorization` (pas de cookie : pas de CSRF). |
| **A08 Intégrité** | Liste blanche des extensions déposables ; **contenu vérifié par signature** (PDF, images, Office/ZIP, médias…) : un fichier dont le contenu ne correspond pas à l'extension est refusé (415) ; **quota de stockage par personne** (`USER_QUOTA_MB`, 1000 Mo par défaut) ; type MIME déduit de l'extension, jamais du client ; téléchargement en `attachment` ; aperçu limité aux images (sandbox CSP). |
| **A09 Journalisation** | Journal d'activité, journal d'accès (12 mois, **conservé en base**, donc durable même si le serveur redémarre) et **journaux métier, sécurité et urgence immuables** (triggers SQL interdisant modification et suppression) ; refus, téléchargements confidentiels et accès d'urgence tracés. |
| **A10 SSRF** | Le serveur n'effectue aucune requête sortante pilotée par l'utilisateur. |

**Annuaire** : les invités ne voient ni e-mail ni date d'inscription des autres membres ; `/health` n'expose plus aucune information de configuration.

**Limites connues** : pas de cookie `HttpOnly` (l'interface Vercel et l'API Render sont sur des domaines différents : le jeton est gardé côté navigateur et protégé par la CSP, la durée de 7 jours glissants et la révocation globale) ; l'administrateur technique garde la lecture des fichiers de niveau « strict » et « confidentiel » (décision de la spécification, à revoir si besoin) ; chiffrement « au repos » assuré par les hébergeurs (Neon et Google Drive chiffrent les données ; vérifiez-le dans leurs conditions) ; pas de double authentification (prévu en évolution).

## Stockage externe (v1.2 · PostgreSQL + Google Drive)
- **Base** : connexion TLS (`sslmode=require`), requêtes paramétrées (aucune concaténation de valeurs utilisateur), journaux et historiques protégés par des **triggers PostgreSQL** (modification et suppression refusées, même par SQL direct).
- **Google Drive** : portée minimale `drive.file` (le serveur ne voit que ses propres fichiers) ; jeton de renouvellement uniquement dans les variables d'environnement ; aucun lien public créé ; téléchargements servis par l'API après contrôle des droits. Le compte Google propriétaire doit avoir la validation en deux étapes.
- **Écritures sérialisées** : file locale **et verrou PostgreSQL inter-instances** (`pg_advisory_lock`) ; les paiements sont de plus **revérifiés dans la transaction** (statut et plafond) : pas de contournement des règles « deux validations » ni de dépassement par requêtes simultanées.
- **Secrets** : `BOOTSTRAP_SECRET` et `JWT_SECRET` se définissent uniquement dans les variables d'environnement de l'hébergeur ; ne les écrivez jamais dans le dépôt ni dans une discussion. Le dépôt est surveillé par Gitleaks et Dependabot (voir `.github/`).
